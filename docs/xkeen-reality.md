# XKeen, REALITY и выбор настроек

Проверка официальных источников: **13 ноября 2026**.

## Выбор профиля при установке

Установщик предлагает **TCP + REALITY + Vision** и **XHTTP + REALITY**.
Для второго варианта Vision/flow не задаётся: Xray может принять JSON с
XHTTP и Vision при `-test`, но отказать при передаче трафика. Оба профиля
проверяются реальным соединением, а не только разбором JSON.
`VLESS_TRANSPORT=tcp|xhttp` задаёт выбор без меню. Для XHTTP сохраняется
случайный `XHTTP_PATH`; сервер, ссылка и роутер используют один путь и mode `auto`.

TLS — защита соединения, XHTTP — транспорт. Поэтому отдельного переключателя
«TLS вместо XHTTP» нет. XHTTP + TLS с собственным доменом требует настройки
DNS, сертификата и его продления; этот установщик не выдаёт такой профиль
без соответствующей инфраструктуры. Выбор транспорта применяется к новой
установке; повторный запуск не переключает работающий сервер. Старые конфиги
при repair сохраняются. После намеренного изменения транспорта клиентские
конфиги нужно переимпортировать вместе с серверной настройкой.

## Скачать файл для Keenetic

Персональная страница `/p/<subId>` теперь содержит кнопку **«Скачать
04_outbounds.json для роутера»**. Прямая ссылка: `/xkeen/<subId>` на том же
HTTPS-хосте и порту раздачи. Файл отдаётся как JSON-вложение с правильным именем.
Ссылка является секретом доступа, как ссылка подписки.

У каждого клиента собственный UUID. Файл формируется из его VLESS-ссылки:
адрес, порт, UUID, публичное значение REALITY, shortId, SNI, fingerprint и spiderX
совпадают с ней. Приватный серверный ключ в экспорт не попадает.
На VPS: `/root/vpn-setup/dist/<name>-04_outbounds.json`.

Экспорт предназначен для **уже установленного XKeen с Xray**. Содержит только
`outbounds`, с тегами `vless-reality`, `direct`, `block`. Оставлены совместимые
поля `vnext`, `publicKey` и `network: tcp` для TCP-профиля; реальный Xray 26.11.9 принимает их.
Для XHTTP используются `network: xhttp` и согласованные `xhttpSettings`.
Новый синоним `password` для REALITY не означает другой ключ или новый пароль.
Внешний REALITY защищает соединение при VLESS `encryption: none`.

Порядок установки на роутере:

1. Сохранить текущий файл **вне** `/opt/etc/xray/configs/`, например в домашнем
   каталоге администратора. Все JSON в `configs` могут объединяться Xray.
2. Положить скачанный файл в `/opt/etc/xray/configs/04_outbounds.json`.
3. Проверить, что существующие правила маршрутизации ссылаются на
   `vless-reality`; другие теги требуют явного согласования конфигов.
4. Выполнить `XRAY_LOCATION_ASSET=/opt/etc/xray/dat xray run -test -confdir /opt/etc/xray/configs`.
   Переменная задаёт каталог GeoIP/GeoSite, который обычно устанавливает служба XKeen.
5. Только после успешного теста — `xkeen -restart`. При ошибке вернуть резервную
   копию. Проверить доступ из клиентского сегмента, DNS, IPv6 и требуемые сайты.

Сам по себе JSON не устанавливает Entware, не выбирает сегмент/политику Keenetic,
не настраивает DNS и не заменяет `inbounds`/`routing`. Версии ядра смотрят через
`xray version` на роутере; версия KeeneticOS — другая версия.
Для новой серверной версии рекомендуется Xray **26.11.9** на клиенте тоже.
Старое ядро может успешно прочитать JSON, но не выполнить современное REALITY
рукопожатие. Установка правильной сборки зависит от архитектуры роутера и используемого
форка XKeen. Автоматически обновлять ядро роутера этот серверный скрипт не будет.

Дополнительная проверка Linux ARM64: клиент 26.2.6 с сервером 26.11.9 передал
трафик с `chrome`, но не с `firefox`. Контрольный тест 26.2.6 на обеих сторонах
прошёл для всех трёх fingerprints, как и тест 26.11.9 на обеих сторонах.
Поэтому старый `firefox` нельзя сохранять при переходе на новый сервер без
обновления клиентского ядра и проверки соединения.

На существующем VPS выполнить `sudo python3 vpnctl.py repair` из нового полного
checkout. После preflight и резервной копии он создаст недостающие JSON и опубликует
новое поколение раздачи. Старые ключи, URL, порт и fingerprint из старой ссылки
сохраняются. Несовпадающий существующий JSON вызывает ошибку, а не молчаливую замену.
`repair` не обновляет панель/ядро и не меняет inbound работающего сервера.

## 443 или 7443

Для **нового** сервера выбран TCP **443**. Это стандартный порт HTTPS; автор
REALITY прямо рекомендует его, хотя протокол поддерживает другие порты.
7443 оставлен отдельным пунктом меню, произвольный порт — ещё одним.
Источник: [ответ автора Xray](https://github.com/XTLS/Xray-core/issues/1807).

Надёжной сравнительной статистики «7443 блокируют реже / живёт дольше 443» для
конкретного российского провайдера не найдено. Нестандартный порт не устраняет
распознавание TLS, блокировку IP/ASN или ограничения исходящего трафика. Выбор
443 — инженерная рекомендация, не обещание срока работы. При занятом порте
установщик останавливается; чужие процессы не завершает. Порт target сайта
остаётся 443 независимо от выбранного входного VLESS-порта.

## Под какой сайт маскироваться

Универсального лучшего домена нет. Официальные рекомендации: TLS 1.3, HTTP/2,
корректный SNI и подходящий сертификат; желательно близость к VPS и, когда возможно,
тот же ASN. Не использовать домен, который только перенаправляет на другой hostname.
Источники: [REALITY README](https://github.com/XTLS/REALITY/blob/main/README.en.md),
[актуальная документация REALITY](https://xtls.github.io/en/config/transports/reality.html).

Меню предлагает `www.microsoft.com`, `www.apple.com`, `www.nvidia.com`, свой
hostname и авто. Это кандидаты для проверки, а не список «неблокируемых» сайтов.
Авто параллельно проверяет сертификат/имя, TLS 1.3, ALPN h2, отклоняет обнаруженный
междоменный HTTP-редирект и выбирает минимальное время TLS среди успешных кандидатов.
Это не проверка совпадения ASN и не измерение устойчивости к DPI. HTTP HEAD может
отличаться от GET в браузере; непроверенный HEAD явно отмечается. Проверка ограничена
таймаутами, не отключает валидацию сертификата и не использует HTTP proxy окружения.
Если все кандидаты не прошли проверку, установка останавливается до создания ключей.

После развёртывания выполняется реальный локальный тест VLESS через экспортированный
outbound. Окончательную доступность проверяют через провайдера клиента.

## Насколько актуальны протоколы и версии

### Если есть собственный домен

Свой поддомен полезен для HTTPS-панели/подписок с сертификатом на домен или для
отдельного профиля VLESS + XHTTP + TLS. Это требует DNS, сертификата и согласованной
настройки сервера/клиента; сам домен не улучшает REALITY и не гарантирует обход блокировок.
Для REALITY он может стать target только при наличии подходящего TLS-сервиса за ним.
Если домен указывает на тот же VPS, нельзя направлять target обратно в тот же
REALITY-listener: отдельный HTTPS-сервис должен слушать другой адрес/порт.
[Описание target в REALITY](https://xtls.github.io/en/config/transports/reality.html),
[сценарии XHTTP](https://github.com/XTLS/Xray-core/discussions/4113).

Текущий установщик сохраняет схему HTTPS по IP. Настройка DNS, доменного сертификата
и дополнительного XHTTP inbound в эту доработку не входит.

### Закреплённые версии

При проверке официального GitHub API последние непререлизные версии:
[3x-ui 3.11.0](https://github.com/MHSanaei/3x-ui/releases/tag/v3.11.0) и
[Xray 26.11.9](https://github.com/XTLS/Xray-core/releases/tag/v26.11.9).
В репозитории ранее была закреплена 3x-ui 3.2.8. Новая установка закрепляет
3.11.0 и отдельно 26.11.9 с SHA256 Linux-64 архива: комплектный Xray в релизе
панели — 26.10.21. Плавающего автоматического обновления на `latest` нет.

`chrome` в Xray 26.11.9 использует обновлённый Chrome 155+ fingerprint. У новых
REALITY-серверов изменилась совместимость ClientHello: поддерживаемые актуальные
отпечатки — chrome/firefox/safari; старые edge/ios/qq нельзя считать заменой.
Меню ограничено этими тремя. Заявление разработчиков о временной устойчивости нового
Chrome к TSPU не является независимым измерением и не обещает будущую доступность.
[Обсуждение и ответы разработчиков](https://github.com/XTLS/Xray-core/issues/7259).

По умолчанию выбран **VLESS + TCP/RAW + REALITY + XTLS Vision**: это
актуальная комбинация и наиболее прямое продолжение существующих конфигов XKeen.
3x-ui — панель управления; транспорт и криптографию реализует Xray.

Есть более новые возможности, но они решают разные задачи:

- **XHTTP** теперь доступен в меню с REALITY. Он умеет разделять направления и работать в сценариях с HTTP/CDN;
  требует согласованной настройки сервера/клиента, иногда собственного домена
  и другой инфраструктуры. Это кандидат на отдельный резервный профиль после
  проверки в нужной сети, а не автоматическая замена рабочего Vision.
  [Описание разработчика](https://github.com/XTLS/Xray-core/discussions/4113).
- **VLESS Encryption**, ML-KEM/ML-DSA добавляют криптографические возможности,
  но сами по себе не доказывают лучшую проходимость DPI. Для постквантового REALITY
  важны также возможности target и совместимость клиентов. В текущий универсальный
  экспорт дополнительные ключи/параметры не включены.
  [VLESS](https://xtls.github.io/en/config/inbounds/vless.html),
  [REALITY](https://xtls.github.io/en/config/transports/reality.html).
- В панели появились другие протоколы, а в свежем Xray — XDRIVE. Новизна и
  число переключателей не дают универсального преимущества для конкретного
  роутера. Существующий резерв AmneziaWG остаётся отдельным вариантом для сетей,
  где проходит UDP. Автоматическая замена всех профилей им не выполняется.

## Что проверяется

- Регрессионные тесты: совпадение клиентских идентификаторов, старый fingerprint,
  добавление JSON без смены старых файлов, отказ при несовпадении, токен и MIME скачивания.
- `tests/smoke_xkeen.py`: реальный Xray принимает экспорт и передаёт HTTP через
  локальный REALITY/Vision сервер для всех трёх fingerprints. Тестовые ключи временные.
- CI Ubuntu 22.04/24.04 выполняет тест ядра и Linux-проверки; bootstrap integration
  использует закреплённые версии панели/ядра, настоящий API и сетевую пробу.

Эти тесты не равнозначны проверке на каждом Keenetic или у каждого провайдера.

Для известного исходника `amneziawg-dkms` из PPA предусмотрено точное
[исправление upstream для новых ядер Ubuntu](https://github.com/amnezia-vpn/amneziawg-linux-kernel-module/commit/70ae2481ca4a0530b500fba976984fa5a22b89aa).
Оно запускается только после неудачной установки пакета, до создания VPN-идентификаторов.
Перед изменением проверяется SHA256 всего исходного заголовка, после — SHA256
официального результата; исходник сохраняется отдельно. Неизвестный исходник
вызывает отказ, повторная установка пакета выполняется максимум один раз.
Это исправление API ядра, не изменение криптографии AWG или параметров обфускации.
Само ядро VPS не обновляется. [Полная проверка установки и восстановления](https://github.com/denis-ne-normis/server-init/actions/runs/43495887190).
