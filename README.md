# server-init — VLESS Reality + AmneziaWG 2.0

Личный VPN на выделенном VPS: два протокола, отдельные клиенты и персональные
HTTPS-страницы с конфигурациями. Ни один протокол/порт не гарантирует обход всех
фильтров. Работа из конкретной мобильной/домашней сети проверяется отдельно.

## Уже установлен старый server-init?

**Не запускайте установщик повторно.** Новый `install.sh` обнаруживает существующие
конфиги, базу панели или сохранённые идентификаторы и останавливается **до изменений**.
Для действующего сервера используется отдельный `repair`.

До резервной копии и изменения служб `repair` сверяет настройки подписок, реальные
AWG key/port/peer list и клиентские экспорты (`.conf`, `vpn://`, VLESS). Устаревший
`vpn://` с другим ключом не будет опубликован вместе с новым `.conf`. Ошибка
preflight означает, что исправление ещё не начиналось; сначала восстановите
согласованные данные. Новая раздача должна пройти локальную HTTPS-проверку готовности,
иначе команда не сообщает об успешном завершении.

Сначала проверьте PR на отдельной VM и сохраните snapshot VPS у провайдера.
Работайте из полного checkout одного коммита: одиночный `curl | bash` больше
не поддерживается, чтобы не смешивать версии вспомогательных файлов.

```bash
git clone https://github.com/denis-ne-normis/server-init.git
cd server-init
# Для проверки PR сначала переключитесь на его ветку/коммит.
python3 -m unittest discover -s tests -v -b
sudo python3 vpnctl.py doctor    # только чтение; старый сервис может получить FAIL
sudo python3 vpnctl.py repair   # снимок данных, сохранение ключей, установка исправлений
sudo vpnctl doctor
```

`repair` сохраняет UUID, subId, серверные/клиентские ключи AWG, PSK, адреса и
параметры обфускации. Он **не переустанавливает пакеты, не меняет firewall и не
пересоздаёт VLESS inbound**. Несовпадающие или потерянные конфиги не заменяются
молча: операция останавливается. Повреждённое состояние восстанавливают из
согласованной резервной копии или явно перевыпускают клиентские доступы.

При первом исправлении может кратко перезапуститься панель 3x-ui и её VLESS.
Сам работающий AWG-интерфейс принимается под управление systemd без `down/up`.
Раздача перезапускается один раз при установке нового unit. Старые персональные
URL сохраняются. Истёкший существующий LE-сертификат сначала продлевается;
неудача ACME не маскируется переходом на self-signed.

Резервная копия создаётся в `/root/vpn-backups/*.tar.gz` (0600), включая онлайн-копию
SQLite, код установленного vpnctl/раздачи, её поколения, ACME-состояние и собственные таймеры. **В архиве есть приватные ключи — не прикладывайте его к issue/PR.**
Изменения других приложений, произвольные настройки панели и неизвестные форматы
старых конфигов не мигрируются автоматически.

## Новая установка

Текущая цель первичного установщика: чистый **Ubuntu 22.04/24.04 amd64**, root,
systemd и заголовки **работающего** ядра. Debian больше не получает Ubuntu PPA:
отдельная поддержка Debian требует отдельной проверенной упаковки AWG.
На Proxmox-хосте, Docker/Coolify-хосте или машине с существующим firewall не запускать.

```bash
sudo env SSH_CONNECTION="$SSH_CONNECTION" bash install.sh
```

Используются 3x-ui `v3.2.8` и acme.sh `3.1.6`; установщики скачиваются по release
тегам, не из `master`. Это фиксация версий, а не проверка подписей всей цепочки
поставки. Версии AWG из PPA и совместимость с ядром нужно проверять на целевой VM.
Скрипт не делает полный `apt upgrade`, не обновляет ядро и не перезагружает VPS.

Параметры через окружение:

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `CLIENTS` | `denis vlad liza parents router svyt` | Имена новых клиентов |
| `CLIENTS_JSON` | не задана | Общие `{name,uuid,sub}` для **нового** сервера |
| `SNI_DONOR` | `www.nvidia.com` | Reality target/SNI; можно изменить при запросе |
| `VLESS_PORT` | `7443` | TCP VLESS |
| `AWG_PORT` | `39743` | UDP AWG |
| `AWG_SUBNET` | `10.9.7` | IPv4 /24, сервер `.1` |
| `AWG_MTU` | `1376` | MTU новой установки; диапазон 1280..1420 |
| `PANEL_PORT` | случайный | HTTPS панели |
| `AGG_PORT` | `2087` | HTTPS раздачи; >=1024 для rootless-сервиса |
| `SUB_PORT` | `2096` | Подписки панели, только loopback |
| `SRV_LABEL` | `S1` | Метка сервера |
| `PUBIP` | api.ipify.org | Явный IPv4 для сервера за NAT |
| `BLOCK_SMTP` | `1` | Блок SMTP и для локального, и для AWG-транзитного трафика |
| `ENABLE_LE` | `1` | `0` — явный выбор self-signed TLS |
| `APPLY_FIREWALL` | `1` | `0` — только изолированная тестовая VM |

Клиентские приватные ключи AWG **не копируются между серверами** через CLIENTS_JSON.
Сначала сохраняется полное новое состояние `/root/vpn-setup/state.json`, затем
рендерятся конфиги. Частично завершённую установку нельзя «исправлять» удалением
state/ключей и повторным запуском: это может отозвать выданные доступы. Для такой
ситуации предусмотрены диагностика и восстановление snapshot, не универсальный
автоматический resume.

## Firewall: отдельная транзакция

На новой установке правила применяются временно. Откройте **второе SSH-соединение**
и выполните напечатанную команду `vpnctl firewall-confirm TOKEN`. Через `sudo`
передайте `SSH_CONNECTION` так, как показано в команде. До подтверждения
`/etc/nftables.conf` не меняется. Без подтверждения через 180 секунд восстанавливаются
предыдущие live-правила. Старый таймер не может откатить более новую транзакцию.

Для **осознанной** миграции firewall выделенного старого VPN-VPS:

```bash
sudo env SSH_CONNECTION="$SSH_CONNECTION" vpnctl firewall-apply --replace-firewall
# Затем из НОВОГО SSH-соединения — команда подтверждения из вывода.
```

Это заменяет весь ruleset и не предназначено для совмещения с UFW/Docker/Proxmox.
`repair` эту операцию не вызывает. Внешний firewall провайдера по-прежнему должен
пропускать фактический SSH-порт, TCP 80 для ACME, VLESS, панель, раздачу и UDP AWG.
На новых установках порт подписок 2096 наружу не открывается. На старом VPS
`repair` сохраняет прежние правила и bind-настройки подписок; их закрывают отдельно.

## Что исправлено в раздаче

`aggsub.py` работает как `vpn-dist`, без доступа к `/root` и серверным приватным
ключам VPN. Публикуется только разрешённый набор клиентских файлов, через атомарное
переключение поколения. В worker выполняется TLS handshake, а не в основном
цикле `accept()`. Ограничены потоки, длительность handshake и **полное** время
чтения HTTP-запроса. Таймаут закрывает обе стороны сокета, чтобы остановить slow headers.

Сервис имеет ограничения systemd на память/задачи/дескрипторы. Это небольшой
специализированный сервер, не полноценная защита от DDoS; для больших публичных
нагрузок нужен отдельный production reverse proxy и ограничения на сетевом уровне.

`/p/<subId>`, `/awg/<subId>` и `/sub/<subId>` сохраняются; добавлен `/vpn/<subId>`.
Путь проверяется точно, неизвестный token даёт 404. Недоступный/пустой/некорректный
upstream даёт 503, не успешную пустую подписку. Порт, путь и HTTP/HTTPS источника
читаются из **реальной базы панели**. Редиректы и proxy-переменные для upstream
отключены; соединение идёт только к loopback. В журнал не пишутся URL с токенами.
Ответы получают `no-store`, `no-referrer`, `nosniff`, `DENY` для iframe.

## Сертификаты и восстановление AWG

`vpn-cert-renew.timer` каждые шесть часов проверяет сам сертификат, а не наличие
каталога acme.sh. При остатке <=72 часов запрашивается `shortlived` с `--days 3`.
Новый TLS-контекст раздачи загружается через SIGHUP без остановки процесса.
3x-ui перечитывает сертификат при перезапуске: обновление сертификата может
кратко переподключить **VLESS**, но не перезапускает **AWG**. Старый cron acme.sh
не удаляется: его hook переводится на управляемое развёртывание уже при `repair`,
даже если сертификат ещё не требует выпуска. Trust-файл HTTPS-подписок также
обновляется при развёртывании сертификата, а не остаётся вечной копией первого сертификата.
Для ACME необходим доступный TCP 80, корректное время и исправный DNS/исходящая сеть.

`vpn-awg-recover.timer` проверяет существование интерфейса, не возраст handshake.
Спящий телефон не является причиной перезапускать VPN всем пользователям.
Пропавший интерфейс восстанавливается только для включённого active/failed unit.
Обычный `systemctl stop awg-quick@awg0` и отключённый unit уважаются.
Watchdog не исправляет блокировку UDP провайдером, неверный MTU, OOM или проблемы клиента.

## Диагностика и проверка перед production

```bash
sudo vpnctl doctor
sudo systemctl status aggsub awg-quick@awg0 vpn-cert-renew.timer
sudo journalctl -u aggsub -u awg-quick@awg0 -u vpn-cert-renew --since '1 hour ago'
```

`doctor` не меняет конфиги. Проверяет сервисы, совпадение AWG-ключей и runtime peer
list, forwarding, сертификат/таймер, страницы, файл AWG и реальную непустую подписку.
Диагностические команды не выводят приватные ключи или персональные URL. Журналы
сторонних сервисов всё равно проверяйте перед пересылкой.

Автотесты запускаются командой `python3 -m unittest discover -s tests -v -b`.
Они используют временные файлы, loopback TLS/HTTP и моки операций с хостом.
CI проверяет Ubuntu 22.04/24.04, синтаксис Bash, ShellCheck и nftables в отдельном
network namespace. Это **не** утверждение об успешной установке DKMS или реальном
VPN-сеансе на этих ОС.

Перед применением на основном VPS (слияние кода не равно проверке самого VPS):

1. Проверить новую установку на отдельной Ubuntu VM, запуск AWG-модуля и импорт
   обоих конфигов реальным клиентом. Подтвердить firewall новой SSH-сессией.
2. Сделать snapshot копии существующего VPS; выполнить `repair`, сравнить хеши
   файлов AWG и UUID/subId до/после. Проверить ранее импортированные клиенты.
3. Проверить reboot, отсутствие неожиданных перезапусков при idle, открытие страниц
   через мобильную сеть и домашний xkeen, а также настоящий AWG handshake/передачу данных.
4. Проверить продление тестового сертификата на staging CA отдельно от production
   лимитов и наблюдать работу после полного цикла обновления сертификата.

Для отката предпочтителен snapshot VPS. Архив содержит старые unit/конфиги/SQLite,
но не является автоматическим rollback всех пакетов ОС. Не распаковывайте его
в работающий сервер без остановки затрагиваемых служб и проверки состава архива.

## Проверки после код-ревью

Добавлены регрессии полного `repair` с изолированными файлами и имитацией операций
с ОС: два последовательных запуска сохраняют байты идентификаторов; неверный
backend/экспорты/истёкший self-signed TLS останавливают миграцию заранее. Проверяются
ротация trust-файла, перенос старого ACME hook без нового выпуска и защита секретов
в ошибках таймаута. CI сохраняет отчёт и архив отслеживаемых исходников на 7 дней;
runtime-данные VPS в CI не передаются. Интеграционная проверка настоящего сервера
остаётся обязательной перед выводом о стабильности соединений.
